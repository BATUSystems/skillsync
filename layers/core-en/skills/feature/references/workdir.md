# Working directory of the run (question at "GO plan")

Read at "GO plan" (without "GO plan": at "GO implement"), when resuming a plan with a `Directory:` line, and when the directory rule touches `CP`, `pr-run` or "YES P<n>".
The instruction core has only the rule; the conditions and failure paths are here.

## The `Directory:` line

The choice is recorded by a plan header line (next to `Run:`, `Handoff:`; [plan](plan-details.md)): `Directory: worktree <directory-name>` or `Directory: main`.
For `worktree` only the directory name is carried, not an absolute path; find the path through `git worktree list` (by name and branch). The line goes into the commit and the PR, so no local paths.
The line is created in the draft plan before the "GO plan" commit (with `specs.tracked: false` the commit does not include the spec and plan, see [spec-store](spec-store.md)). Resuming reads it: no `Directory:` line in the plan = worktree as before;
a vanished worktree directory from the plan line = STOP and a question (recreate from the branch?), no silent switch to `main`.
Resuming with `Directory: main` checks the conditions again before the first commit (the directory question is not asked, and the branch or HEAD may have changed between sessions): detached HEAD = STOP; a live lease of another run = STOP with a worktree proposal; current branch different from the one at the run's previous commits = STOP with a question naming both branches; branch equal to `delivery.base` in `pr` = STOP ("main" is not accepted); in `direct` on the base, a warning as at selection and a question about continuing.

## The question

At "GO plan" (without "GO plan": at "GO implement", the first consent word that assumes a directory) the session asks one question with two options (a host with a choice window: the window; without it a text question):
"Where to work on this run?": "own worktree" (default, recommended: file isolation, parallel sessions, no risk to the current branch) or "main checkout" (one directory, no second copy).
The directory question gives the name of that branch (the current one in the main checkout); for `delivery.base` and for `main`, `master` and `develop` it warns that commits and `CP` will go to the base or main branch.
No answer, refusal or cancellation = no "GO plan": nothing is created, no commit and no `Directory:` line (the spec stays `draft`, unless the `skillsync spec approve` button has already set `approved`; the row of the resume table in [spec](spec.md) for a spec that is `approved` (button or `skillsync spec approve`) without a plan or with a draft plan without `Spec-sha` handles this state).

The question is not asked: (1) when the plan already has a `Directory:` line (resuming, a repeated "GO plan" after a spec change); (2) in card mode (`ASSIGN`/`dispatch:`) the directory follows from the work order, by default the package worktree, the card does not ask
(the card (worker-mode) always works in the worktree from the work order, [worker mode](worker-mode.md)); (3) on entry from a ticket key (`pr-after-approval`): "do the PR" uses the current branch and does not create a worktree, unchanged ([entry from a key](pr-after-approval.md)).

## `worktree`

As before: a separate working tree and working branch ("GO plan" creates it if it does not exist), a copy of the untracked spec draft, the manifest and `skillsync link` according to [worker mode](worker-mode.md).

## `main`: entry conditions

The working branch is the current branch of the main checkout, any one, also `delivery.base`, without `git switch`. The "GO plan" commit is created on it in the main checkout, `git add` only with explicit paths, never generated files.

- Detached HEAD = STOP with a worktree proposal (no branch, no `CP`, no PR).
- Changes in tracked files (other than files generated by `link`) = the question "continue with these changes in the tree?"; the list of these changes goes into the plan baseline, and the default answer is "use a worktree" (not stash, not `checkout --`).
  A file from the baseline that a plan step also changes = a question or STOP (no mixed commit: `git add <path>` would commit the user's changes).
  Untracked foreign files: baseline without a question.
- A live lease of another run in this directory (`.skillsync/claims`) = STOP and a worktree proposal.
- In `pr` mode with the current branch equal to `delivery.base`, "main" is not accepted (a PR from the base to the base does not exist); the question then offers only an own worktree or the user switching to another branch in the main checkout.
- `direct` mode on the base: no question about `Handoff:` and no such line (working = base, nowhere to hand over); `CP` pushes the current branch that is the base (the rule "never to `delivery.base` … unless the working branch is it"). With a branch other than the base, the question and `Handoff:` as before.

## Effects on other rules

- `pr-run` step 3 with `Directory: main` uses the main checkout and its current branch (it does not create a worktree or branch), provided the branch is other than `delivery.base`; step 8 skips `main`.
- In `pr` mode with `main`, before using the current branch check for an existing PR and an upstream with foreign commits (there are some = a question). `pr-run` step 3 has a branch naming convention (e.g. with the ticket key); the current branch need not satisfy it, but the question shows this.
- `CP` unchanged (push of the current working branch to its remote counterpart). A push to the base, fast-forward `working:base`, also works from the main checkout; the main checkout is updated with `--ff-only` only when clean and on `base` (when the current branch is the base, `CP` pushes it directly; with another branch this update is inactive).
- The copy of the run outside the worktree and worktree cleanup concern only `Directory: worktree`; with `main` the run stays in the project directory.
- With `specs.tracked: false`, worktree cleanup requires `skillsync spec snapshot --check --to <copy root>` with `PASS` (the spec and plan are not in git; removing the worktree alone loses them, [spec-store](spec-store.md)); the "GO plan commit" then covers only tracked files.
- In `direct` with `Directory: main`, "YES P<n>" works (main checkout); in `pr` the proposals `repo: project` stay `deferred` as before ([retro-quality](retro-quality.md)). "YES" after the final record changes HEAD and invalidates the `sha` of the `CP` consent (existing rule: different `sha` = a question).
- Reversal: `main` does not change the branch; the "GO plan" commit is local, reversible by `git reset` only with the user's consent; after handing over to the base in `direct` from a working branch, the session proposes `git switch <base>`, it does not do it itself.
- A second session or an IDE in the same main directory (lesson `zmiana-head-w-trakcie-biegu-uniewaznia-bieg`): commits land on the branch this session has selected; that is why the question warns, and a live lease ends in STOP.
