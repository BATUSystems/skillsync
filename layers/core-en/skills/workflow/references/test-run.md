# Plan step tests through skillsync (`test-run`)

The source of truth for roles and skills: the tests of a plan step are run **through skillsync**, so that the status page shows their result (the “Tests” tab, the bar at the step), and the gate can check that the step had tests.

## Command

`skillsync test-run <project> --run <run id> --step <step id> -- <test command>`

- the command and its output stay unchanged; the `test-run` exit code: PASS 0, `FAIL` (command code ≠ 0) = the command's code, 124 when `--timeout` is exceeded, 127 program missing; a run with command code 0 without a recorded `PASS` (`BLOCKED`: no positive test count, skipped without consent, “code 0, but the output reports failures”, unexecuted Karma specs; or no status record after a write error or an interruption) ends with code 2 and a stderr line `test-run: exit code 2: …`; 2 is also BLOCKED before the start, so a command code of 2 is indistinguishable from BLOCKED by the code alone: the stderr line tells them apart (`test-run: step <id> (<source>), attempt <n>: <STATUS>`, `BLOCKED: …`); `--import` returns 0 on a correct import regardless of the run status; code 0 is lifted only by `--allow-no-count <reason>` (no counters) and `--allow-skips`; zero tests executed, “code 0, but the output reports failures” and unexecuted Karma specs have no lifting by any flag (fix the test command);
- `--run <id>` (also with `--import`) requires a trace of the run in `.skillsync/runs/`: a directory `<id>/` (not a link) or a regular file `<id>.json`, the exact name; without a trace `BLOCKED` (code 2) with `--run <id>: no such run in .skillsync/runs/ (runs: …)`, nothing is written, the command does not start; a run is created by `skillsync checkpoint` (with `--import` the run may also be copied); without `--run` the only run directory is chosen (a record and a link do not count);
- events are written to `.skillsync/runs/<run>/tests/<step>/<n>.jsonl`; the list of tests after completion comes from a JUnit XML or TRX report (`--junit <file|directory>`, or the default dotnet, Maven, Gradle locations), counters from the output (e.g. Karma “Executed N of M”);
- exit code 0 with output that reports failures in a known summary (`FAILED (failures=N)` of unittest, `N failed ... in Xs` of pytest; with the counter source `regex`, that is without an adapter and without a JUnit report, also the anchored summaries of Playwright (`  N failed`, `  N interrupted`), Vitest (the `Tests` line with `N failed`, not `Test Files`) and Jest (`Tests: N failed,`, anchored only on the left)), is `BLOCKED` with the reason “a pipe, `|| true` or a wrapper may hide the test exit code” (code 2); a plain phrase “3 failed attempts”, “0 failed” or “Test Files  1 failed” does not redden a green run; there is no lifting flag, the workaround: fix the command or give `--format` or a `--junit` report;
- SIGTERM (POSIX; CTRL_BREAK on Windows) interrupts the run like Ctrl+C: the command's process tree ends, `end` has status `BLOCKED` (`test-run` code 2), the step lock is released; closing the console window or `taskkill /F` on Windows gives no chance to clean up (a limit);
- `PASS` only with a known positive count of executed tests (as in `validate`): zero tests, an unknown count and skips give `BLOCKED`; explicit and recorded exceptions: `--allow-no-count <reason>` (only an unknown count), `--allow-skips` (skips); zero executed tests has no exception;
- a wrapper (e.g. a shell script wrapping the test command) must pass on the command's exit code (e.g. `exit $LASTEXITCODE`); the wrapper's code 0 despite a test error gives `PASS` with `--allow-no-count` or with a counter `N passed` in the text (without them `BLOCKED`), that is without evidence beyond the exit code; exception: output with a Playwright, Vitest or Jest failure summary from the previous point gives a `BLOCKED` that the flag does not lift. `--allow-no-count` verifies nothing: the exit code is guarded only by the command's code. Counters from an unrecognized command (`tool: unknown`) come from loose expressions over the whole output. With wrappers point to the adapter through `--format` (tool recognition does not see commands behind `powershell -File`). Before using a wrapper check it with a command that fails: `exit 3` must give FAIL with code 3;
- `validate --run` and `smart-test --run` do NOT record test events: run the tests of a plan step through `test-run`;
- a runner that `test-run` does not recognize (e.g. `vstest.console.exe` for .NET Framework) writes its report to a directory `test-run` does not know. Point to it with `--junit <file|directory>`; the test counts then come from TRX or JUnit. If the result is still `BLOCKED`, fix the command or the report. With an unknown test count and code 0 you may give an explicit `--allow-no-count <reason>`. When the tests cannot be run through `test-run`, close the `[T]` step with `checkpoint --no-tests <reason>` and describe it in the “Result”. Do not assemble a TRX report, a `tests/<step>/<n>.jsonl` file or a step record by hand: such a write bypasses the `[T]` gate and is not evidence.

## Which step and which run

- The brief for a subagent **contains `--run` and `--step`**; without `--step` the command picks the only step marked `in progress:` in the checkpoints, and with several `in progress:` steps it ends `BLOCKED` (code 2): do not guess.
- Runs without a step go to the “No step” section.

## Gate of `[T]` steps

A step marked `[T]` in the plan (at the beginning or end of the title in `## Progress` or in the `Step` cell of the table) is not closed without evidence: `checkpoint --status PASS --step <id> --evidence .skillsync/runs/<run>/tests/<step>/<n>.jsonl` accepts only the record of a passing `test-run` of THIS step and run, executed on the current content (working tree without `.skillsync/` and `docs/plans/`): the registry records the tree fingerprint at the **start** (`start.treeStart`) and at the **end** (`end.tree`) of the run and both must be equal, so a file changed during the run (also one generated by the tests and not listed in `.gitignore`) is not evidence (the message names the changed paths from `end.changed`, see “Event contract” below); with several attempts of this step on the same content the NEWEST decides (an older green run does not beat a newer red one); a run imported from another machine is valid only for the commit with `--source-sha` and with a clean tree (no uncommitted changes). Waiver: `--no-tests <reason>` (recorded in the record, a `doctor` warning `tests-waived`, `needsHuman: tests`: a human decision at closing). The gate protects against skipping tests, not against forging the evidence file. `doctor` also warns about a step with tests without `[T]` (`tests-step-not-marked`) and about a `[T]` step ticked without a run (`tests-not-run`). A `[T]` step is considered done when it has a `- [x]` row in the checklist or the last `checkpoints` entry of this step in the run record has status PASS; thanks to this `tests-not-run` also works for plans with a step table, which have no `[x]` rows.

## Event contract

File `.skillsync/runs/<run>/tests/<step>/<n>.jsonl`: one line is one JSON event (`v: 1`), types `start`, `collected`, `test`, `counts`, `end` and `import` (appended by `test-run --import` to a run from another machine). Fields read by the gate and the status page:

- `start`: `treeStart` (fingerprint of the working tree before the tests), `command` (always masked), `run`, `step`, `attempt`.
- `end`: `status` (`PASS`, `FAIL`, `BLOCKED`), `exit`, `reason`, `counts`, `source`, `tree` (fingerprint of the tree after the run), `truncated`. Optional `changed`: a list of up to 5 paths that differ between the tree at the start and the tree at the end; written when the trees differ and the paths can be read. Each path up to 300 characters, always masked on write (regardless of `tests.mask`) and again on read. Older files have no such field; the gate message then gives no paths.
- `import`: `sourceSha` (the commit for which the imported run was produced; the gate compares it with HEAD).
- The tree fingerprint (`treeStart`, `tree`) is a git tree id. New objects (blobs, trees) go to a temporary directory in `$TMPDIR` (with changed, untracked and non-ignored files it may take a lot of space), which the run keeps from start to end and removes; the repository's object database is only read (alternates). The tree id does not change because of this.
- The event file is untrusted data (it may come from another machine through `--import`). The `changed` field is only displayed: it never goes into a git command or any other command; the reader rejects every other shape of this field.

The `checkpoint --status PASS` gate for a `[T]` step, when the tree changed during the run, writes: “files changed WHILE the tests ran (tree … at the start, … at the end; changed: a, b)”; without the `changed` field the “; changed: …” part is empty.

## Tool output adapters (phase 2)

The module `skillsync_workflow/test_adapters/<tool>.py` reads the lines of the test command's output (`feed`) and the report files after it ends (`end`) and reports what it understood only through `ctx.emit` (`collected`, `test`, `counts`); the event file, the mask, the limits and the exit code are handled by the recorder (`test_run.TestRecorder`). An adapter that does not understand the output emits nothing, and the run stays with the counters from the summary and the report. The adapter's `live` field says how much is visible during the run: `running` (the state of individual tests live), `completion` (the list after completion) or `counts` (counters only); `partial` passes on an unfinished end of a line (the tool prints `test_x ... ` at the start of a test and `ok` at its end). An exception in an adapter disables it for this run; `end()` returning `True` skips reading the report. Test names and identifiers have `/` instead of `\`; a test without a result after the end of the run is not “run”, it is “pending”.

Table of adapters (full rules and limits: `docs/test-adapters.md`):

| Adapter | Choice under `auto` | `live` | Final source |
|---|---|---|---|
| `unittest` | `python -m unittest -v` | `running` | output summary |
| `pytest` | `pytest -v` (without `--collect-only`) | `running` | `--junit-xml` (the same ids) |
| `cargo-test` | `cargo test` | `completion` | state from the line |
| `cargo-test-serial` | `cargo test` with `--test-threads=1` | `running` | state from the line |
| `dotnet` | `dotnet test` | `completion` | TRX |
| `vitest` | `vitest …` (without `ng`) | `completion` | JUnit (only with `--junit`) or the stream |
| `karma` | `karma …` (without `ng`) | `counts` | JUnit (names) and counters from the stream |
| `playwright` | `playwright test` | `completion` | stream |
| `cypress` | `cypress run` | `completion` | stream |
| `angular` | `ng test` | `counts` | like `vitest` or `karma` |
| `tap` | never: only `--format tap` (a bare script, `npm test`, `bats --tap`, `prove`) | `completion` | stream |
| `node-test` | `node --test` with the `tap` or `spec` reporter (or without a reporter) | `completion` | stream |

`node --test` prints TAP (Node 20 and 22 in a pipe) or `spec` (Node 24; TTY: spec). `node-test` recognizes the format by the first significant line. When `auto` does not choose an adapter, use `--format <name>` (e.g. `--format tap` for a script that prints TAP).

A new adapter is a new file (the registry discovers modules by itself), with a fixture of the tool's output in `tests/fixtures/test-runs/` (without home paths, machine names and session identifiers) and a test through `tests/adapter_harness.py`.

## Hook warning about bare test commands

A project with an agent flow has in the PreToolUse hook (`.claude/hooks/guard-commands.py`) a second part (`hooks.guard_tests`, default `warn`): when a Bash command runs a **wide test run** outside `skillsync test-run` (without a filter and without a file: `python3 -m unittest discover`, `pytest`, `dotnet test`, `cargo test`, `ng test`, `npm test`, …), the model gets a warning in its context. The warning **does not block** and arrives together with the command's result, that is after it ran: this run is not evidence of a `[T]` step, repeat it through `skillsync test-run`. A targeted run (a file, a filter, a test name, fewer than `hooks.wide_modules` modules) and print-only commands (`--collect-only`, `--list-tests`) get no warning, and neither do wrappers (`skillsync test-run|validate|smart-test`, `systemd-run …`, `flock <lock> systemd-run …`, `skillsync validate|smart-test … --run`, `hooks.test_wrappers`; `flock` alone without `systemd-run` is not a wrapper). A one-time skip, only with the user's consent: `SKILLSYNC_GUARD_EXCEPT='<reason>'` before the command (a trace in `.skillsync/hook-exceptions.jsonl`, field `kind: ["tests"]`).

**Limits (honestly).** The hook reads the command text and recognizes the tool by the **program** (the first word after the wrappers from the `test_tools.json` table, including `poetry|pdm|pipenv run` and `env -S`; when that first word is a “host” `python*`, `py`, `pypy*`, `coverage`, also the word after `-m`: `python3.12 -m pytest`, `python3 -X dev -m pytest`, `py -3 -m pytest`), not by a word in the line. Copies of the hook script and the `test-tools.json` table lie next to the hook; after updating the core run `skillsync link` to refresh them (new wrappers and `env -S` depend on the table, the `-m` step and new verdicts on the script). It does not see: `./scripts/test.sh`, `devbox run`, `docker exec`, `tox`/`nox` (`tox` is in the table as a tool, but the hook has no wide-run rule for it), `make` with a target other than `test|check`, commands through `sudo`, `nohup` or another wrapper outside the table (also `sudo pytest`: the hook classifies the program, not a word in the line), `-m` after a script (`python tools/run.py -m pytest` gives a `wide` warning, because the hook does not know whose argument it is), commands after `nohup` in `env -S 'nohup python -m unittest'` (the cause is `nohup`, not `-S`: `env -S 'python3.12 -m pytest'` gives `wide`; words split from `-S` are not read only by steps 2–4 of the `detect_tool`/`tool_of` functions, which work on the raw argv), a narrow pattern in `unittest discover -p`, a remote command (`ssh host '…'`), a script written with the Write tool and run afterwards; `npm|pnpm|yarn test` gets a “probably” warning (the hook does not read `package.json`), `dotnet test` on one small project also warns (the hook does not know the size). On Windows the command is read the way Git Bash reads it (as in the removal part): an unrecognized form means no warning, never a block. The effectiveness of the warning in a live session (whether the model sees it) is NOT_VERIFIED until measured; it is complemented by the `checkpoint` gate of `[T]` steps, which is evidence, whereas the hook is not. An error in this part of the hook (a missing or damaged `test-tools.json`, a classifier error) silences only it: the denial of permanent removal works unchanged.

## What not to do

- Do not paste failure messages or test names from the files `.skillsync/runs/**/tests/` into content leaving the machine (a PR description and comment, `## Result`, reports in the repository, messages between sessions, a tracker): give the counters, the test `id` and the path to the run file. Test results are not masked (`tests.mask`, `docs/security.md`).
- Test commands run by hand are not evidence of a `[T]` step and are not visible on the page (the hook warns about a wide run, see above).
