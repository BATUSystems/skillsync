# 180-A: koszt strony statusu przy 5000 testów (F5.2)

Pomiar: Linux, Python 3.14, jeden proces; plik zdarzeń jednej próby z 5000 testów (co 50. nieudany z komunikatem 5 linii), 679 KiB,
grupy po 100 testów. Skrypt syntetyczny: `EventWriter` → `dashboard_tests.build_tests`, `finalize_status`, `tests_response`, `finalize_response`.
Czas = średnia z 5 powtórzeń, CPU = `time.process_time` (jeden wątek, więc wall ≈ CPU).

| Operacja | Przed (redact czyta środowisko dla każdego napisu) | Po (środowisko raz na wywołanie) |
| --- | --- | --- |
| `build_tests`, pierwszy odczyt pliku | 48 ms | 30 ms |
| `build_tests`, odczyt z pamięci podręcznej (plik bez zmian) | 5,8 ms | 3,4 ms |
| `finalize_status` (cała odpowiedź `/api/status`, 50 KiB JSON) | 411 ms | 6,6 ms |
| `tests_response` 500 testów / 5000 testów | 2,5 / 5,8 ms | 1,9 / 4,1 ms |
| `finalize_response` 500 testów (`GET /api/tests` domyślnie) | 1186 ms | 12 ms |
| `finalize_response` 5000 testów (`limit=5000`) | 10 116 ms | 102 ms |

Wniosek: koszt dawał `common.redact`, który dla każdego napisu i klucza przeglądał `os.environ` (kilkadziesiąt wyrażeń regularnych).
Poprawka w `redact` (lista sekretów środowiska budowana raz na wywołanie, wyrażenia skompilowane na poziomie modułu; semantyka bez zmian,
środowisko czytane przy każdym wywołaniu) zamiast osobnej pamięci podręcznej drzewa `tests` według sygnatury pliku: odświeżenie strony
kosztuje kilka milisekund, więc dodatkowy bufor nie jest potrzebny. Pilnuje tego test `EnvironmentReadOnce` w `tests/test_skillsync_redact_patterns.py`.
