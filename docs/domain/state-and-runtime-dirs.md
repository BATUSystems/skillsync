Reguła:
- `.github/.skillsync-state.json` — stan generatora w trybie copy: klucze `github-skill:<n>`, `claude-skill:<n>`, `claude-agent:<n>.md`, `codex-skill:<n>`, `codex-agent:<plik>.toml`,
  `codex-instructions:skillsync-instructions.md`; wartość = hash biblioteki z chwili kopiowania (baza porównania trójstronnego). Lokalny, dopisywany do `.github/.gitignore` przy pierwszym zapisie.
- `.skillsync/` — lokalny stan workflow (logi `logs/<uuid>/`, `cache/smart-test/`, `runs/<run-id>.json`, `environments/`, `e2e/`, `claims/`, `upgrade/`, `providers/`, `dispatch/<run-id>.yaml`, `locks/`, `audit/`).
  Nigdy nie jest commitowany: `link` dopisuje `.skillsync/` do `.gitignore` projektów z `feature`.
- `runs/` (przebiegi): `<id>.json` i `<id>.lock`; `id` musi pasować do `_slug` (`[A-Za-z0-9][A-Za-z0-9_.-]{0,79}`). Ścieżka przez `runs.py:_store_path` (zakaz dowiązań w `.skillsync`, `runs` i samym pliku). W dispatch `<run>.<paczka>`; ponowienie `<run>.<paczka>.2` to ta sama tożsamość logiczna.
- `runs/<id>/` to katalog raportów przebiegu: tworzy go procedura, nie `checkpoint`. `retro` czyta go tylko jako sygnały (liczniki statusów), nie jako rekordy. `metrics --classify` używa go wyłącznie do wykrycia `no_data`. Katalog nie zastępuje pliku `<id>.json`; katalog bez przypisanego pliku `<id>.json` (lub `<id>.*.json`) to przebieg `no_data`.
- `retro` i `retro-scan` nic nie zapisują (ani plików, ani katalogów). Przy szukaniu katalogów pomijane są `*.lock` i `*.json` (`runs.py:_scan_dirs`).
- Pliki retro przebiegu leżą w `runs/<id>/` i są poza gitem: `retro-signals.json` (sygnały i propozycje, zapisuje orkiestrator), `retro-decisions.json` (historia stanów propozycji, schemat 1), `retro-P<n>.diff` albo `retro-P<n>-<k>.diff` (diff propozycji). Plik wejścia skanu (np. `retro-scan-input.json`) też leży w katalogu przebiegu; jego nazwę wybiera orkiestrator. Nie jest zamrożony i nie jest dowodem checkpointu.
- `retro-decide --proposal` dopisuje wpis do `retro-decisions.json` w katalogu przebiegu, a potem zapisuje sekcję `proposals:` w rejestrze `docs/retro/decisions.yaml` (śledzony w gicie). Każdy zapis jest atomowy; kolejność i stany: [retro-proposals.md](retro-proposals.md).
- Pozostały stan przechodzi przez `storage.py:state_path`: zakaz symlinków i ścieżek poza projektem; zapis atomowy (plik tymczasowy + `os.replace`), JSON ≤ 2 MB. Przebiegi mają własną kontrolę ścieżki (`runs.py:_store_path`) i ten sam limit 2 MB (`runs.py:_write`, `_read`).

Dlaczego: stan i dowody są per maszyna i per stan kodu; dowód związany jest z fingerprintem (HEAD + diffy + pliki nieśledzone, z wyłączeniem `.skillsync/`).

Wyjątki i przykłady: cache `smart-test` zapisuje plan, nigdy wynik wykonania — wyniki wymagają świeżego uruchomienia. `checkpoint` blokuje zapis katalogiem `<run-id>.lock`; po awarii procesu zostaje i trzeba go usunąć ręcznie.

Strona statusu (zakładka „Historia”) i CLI zapisują w korzeniu katalogu roboczego dwa katalogi stanu, oba w drzewie gałęzi (katalog `.skillsync` może pochodzić z repozytorium, także jako zacommitowane dowiązanie), więc ich pliki powstają ostrożnie: `status.state_subdir` i `dashboard_history._state_dir` odmawiają dowiązania symbolicznego na drodze (`.skillsync` i podkatalog), katalogi dostają prawa 0700, a pliki otwiera się z `O_NOFOLLOW`:
- `.skillsync/locks/plan-status.lock`: blokada plikowa (`FileLock`, plik usuwany pod blokadą) każdej zmiany statusu planu lub specu. `set_doc_status` bierze ją sam, więc chroni CLI `plan archive|approve` i przyciski strony, nie edytor (zapis ręczny jej nie zna). Zajęta po 5 s = błąd `locked by another writer` (CLI: `BLOCKED`, kod 2); zmiana ze strony czeka 3 s, potem 409 `locked`. Trzymający blokadę woła `set_doc_status(..., lock=False)`: blokada nie jest wielowejściowa.
- `.skillsync/audit/plan-status.jsonl`: audyt zmian statusu ze strony (JSON Lines): wiersz `intent` przed zmianą, `done` po niej (z nowym `sha` i `shaBefore`), a przy nieudanej zmianie po intencji `failed`; pola `{at, by, via, tab, path, from, to, sha, phase}`. Dopisanie bierze własną blokadę `plan-status.jsonl.lock` w tym katalogu, odmawia pliku niezwykłego (dowiązanie, FIFO, katalog) i kończy `fsync`. Limit 1 MiB bez rotacji: po jego wyczerpaniu archiwizacja kończy się `auditRefused` (500, nic nie zmieniono) do ręcznego przycięcia pliku. Plik jest per zakładka i znika razem z usuniętym worktree.

Poza projektem, w katalogu danych maszyny (`layers.data_home()/dashboard/`, 0700 użytkownika; nie w drzewie projektu i nie w gicie), leży stan serwera strony statusu:
- `<skrót root>-<port>.json`: plik stanu serwera, `schema: 2` (`pid`, `port`, `root`, `approvals`, `token`/`tokenId` tylko przy zgodach, `role`, `peer`, `bind`, a dla serwera zakładek `kind`, `serverId`, `commonDir`, `tabs[]` z id, ścieżką i tokenem zakładki, `terminal`), 0600, zapis atomowy (plik `.tmp-…tmp`, potem `os.replace`), usuwany przy zamknięciu serwera tylko przez proces o zapisanym `pid`; `tabs[]` odświeża serwer przy każdej zmianie listy zakładek. Skrót to 16 znaków `sha256` ścieżki `root` (w projekcie git głównego katalogu); `servers()` czyta schema 1 i 2, a serwer projektu znajduje się po `commonDir`, nie po nazwie pliku. Pole, kontrakt i `dashboard url`: `docs/dashboard-contract.md`.
- `<serverId>-pins/<id>.json`: plik przypięcia (`{path, at[, plan]}`, ≤ 4 KiB) zapisany przez `dashboard serve` w innym worktree projektu, żeby serwer dopisał jego katalog jako zakładkę. `serverId` to 16 znaków szesnastkowych procesu serwera, `id` to id zakładki (`^(main|[0-9a-f]{12})$`). Katalog 0700, plik 0600, czytelnik odmawia dowiązań (`O_NOFOLLOW`), cudzych właścicieli i nazw spoza wzorca; plik znika z wyrejestrowaną zakładką i przy zamknięciu serwera, a katalogi po zabitym serwerze sprząta start następnego (`sweep_pins`). Reguły rejestru: [dashboard-server.md](dashboard-server.md).

Stan dyspozycji `.skillsync/dispatch/<run-id>.yaml` zapisuje wyłącznie skill `dispatch` — generator go nie tworzy ani nie waliduje.
