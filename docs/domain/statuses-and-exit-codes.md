Reguła: komendy workflow zwracają status operacji, nie projektu: `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN`. Wyjście: `PASS`/`NOT_RUN` → 0, `FAIL` → 1, `BLOCKED` i nieznany → 2.
Wyjątki w handlerach kończą się `skillsync: <komunikat>` i exit 2 (także brak configu). `resume`: 2 przy nieaktualnych dowodach/źródłach lub kroku ≠ PASS. `benchmark`: 0/1/2 dla PASS-NOT_RUN/FAIL/BLOCKED.
`retro` (tylko odczyt): `PASS` i `NOT_RUN` → 0; `BLOCKED` → 2 (nieczytelny plik w zakresie albo `--run-id` bez przebiegu i katalogu, z wynikiem `{status, reason, run_id}`). `retro` nie zwraca `FAIL`. Nieprawidłowy `--run-id`, brak manifestu i dowiązanie `.skillsync` lub `.skillsync/runs` to `skillsync: …` z exit 2.
`retro-scan` (tylko odczyt): `PASS` → 0, także z ostrzeżeniami i `truncated: true`; `BLOCKED` → 2 z `reason` (błędne wejście `--signals`, niepoprawny rejestr `docs/retro/decisions.yaml`). Błąd argumentów to JSON `BLOCKED` z kodem 2. Błędy obcych źródeł nie dają `BLOCKED`: źródło jest pomijane z ostrzeżeniem `source-skipped:`, a przebieg z ostrzeżeniem `unreadable-run:`. Ostrzeżenia: `unknown-key:S<n>`, `no-cause-keys`, `ref-not-in-history:<id>`, `ref-unverified:<id>`, `unreadable-run:<id>`, `source-skipped:main-checkout`, `source-skipped:project`, `truncated`; kodu wyjścia nie zmieniają.
`retro-decide --proposal`: `PASS` → 0; `BLOCKED` → 2 z `reason` i `writes` (`run`, `registry`: `written`, `failed` albo `skipped`). Przy odmowie przed zapisem `writes` ma `skipped` dla obu zapisów; po częściowym zapisie `writes` mówi, który przeszedł.
`checkpoint --final` bez retrospektywy: exit 0, także przy ostrzeżeniach `retro-quality-missing:` i `retro-quality-unverified:` w `warnings`.
`dispatch` (tylko odczyt): `PASS` i `NOT_RUN` (brak lub pusty `.skillsync/dispatch`) → 0; `BLOCKED` → 2 (dowiązanie `.skillsync`/`.skillsync/dispatch`, brak manifestu, zły `--run-id`); nieczytelne pliki to wpisy `unreadable`, nie błąd (zob. `dispatch-state-view.md`).
`prototype init|sync|index|list`: `PASS` → 0, `FAIL` → 1 wyłącznie w `sync --check` przy rozjeździe plików, `BLOCKED` → 2 (walidacja, odmowa, brak zasobów, błąd prototypu; także wyjątki akcji). `BLOCKED` ma pierwszeństwo przed `FAIL` (`sync --check` z uszkodzonym prototypem = 2, lista `failed` i `stale`). Błąd argparse (brak `<projekt>`, `--requirements`, nieznana akcja) to exit 2 z usage na stderr, bez JSON (zob. `prototype-manifest-and-cli.md`).
`prototype ids|migrate|serve|user` (ten sam `emit`/`exit_code`): `ids --check` (domyślnie) → `FAIL` (1) przy brakujących, zduplikowanych lub nieprawidłowych `data-proto-id`, `PASS` (0) gdy komplet; `ids --fix` → `PASS` także z pozostałymi duplikatami (lista w `warnings`); `--check --fix` razem, `--password-prompt --password-stdin` razem i inne błędy argparse → 2 z usage. `migrate` (także `--dry-run`) → `PASS` albo `BLOCKED` (2) bez żadnego zapisu: nieczytelny `comments.js`, nieznany slug, uszkodzony `comments.json`, a bez `--allow-skipped` także każda pozycja `skipped` (operacja, której v2 nie przyjmie; obcy `prototypeId`, `version` ≠ 1 albo `operations` niebędące listą przy niepustym logu; wpisy odrzucone przez normalizację v1; przy istniejącym `comments.json` operacje pozostawionego `comments.js`, których w nim brak) oraz istniejący już `comments.v1.js`, gdy migracja miałaby go utworzyć; z `--allow-skipped` pozycje `skipped` dają `PASS` z ostrzeżeniem i `comments.v1.js`; `already_migrated` to `PASS`. `serve` → 0 po Ctrl+C (JSON `PASS` na stdout), 2 przy odmowie `startup_checks` (plik użytkowników w `root`, brak pliku, tryb szerszy niż 0600, śledzony lub nieignorowany przez git) albo zajętym porcie. `user add|passwd|remove|list|import` → 0, a `BLOCKED` (2) dla błędnego adresu, hasła < 10 znaków, loginu zarezerwowanego, braku `prototype.default_password`, configu lub pliku użytkowników szerszego niż 0600. Moduł samodzielny `prototype_server.py`: `serve`/`user` kończą 0 lub 2.
`prototype accept` (`--screen`/`--all`/`--project`, ten sam `emit`/`exit_code`): `PASS` (0) z `accepted` i `skipped`; `BLOCKED` (2) z `error` i `reason`: `tty_required` (stdin nie jest terminalem albo hasła nie wpisano; bez terminala nie ma pytania o hasło), `forbidden` (`--by` bez konta albo bez roli `acceptor`/`developer`), `password_change_required` (`mustChange`), `invalid_credentials`, `unknown_screen` (także przykład), `writing_in_progress` (ważny marker zapisu), `needs_migration` (v1 przy `<slug>`), `prototype_not_found`, `write_failed`; w `--project` także z `accepted` i `pending`. Nigdy `FAIL`; `accept <projekt> <slug> --project` = `BLOCKED` exit 2 z JSON-em (po kontroli TTY), a `--project <slug>` (slug po opcji) = błąd argparse, exit 2 z samym usage; ekrany z niejednoznaczną sekcją trafiają do `skippedScreens` (PASS). `prototype gate` (`--plan` albo slugi, tylko odczyt): `PASS` (0; też z obejściem `bypassed`), `FAIL` (1) z `missing` (`reason`: `brak`, `nieaktualna`, `needs_migration`, `brak_ekranow`, `niejednoznaczny_ekran`, `writing` = ważny marker zapisu, `screen: null`), `BLOCKED` (2) z `error`: `prototype_not_found`, `invalid_prototype_line` (także bliskie literówki wiersza `Prototyp:`), `invalid_bypass_line` (także zła data), `plan_unreadable`, `prototype_unreadable`, kod błędu odczytu `comments.json` (np. `invalid_log`), `gate_failed` (wyjątek przy ocenie bramki w `readiness`). `gate --plan PLIK --phase Fn` (kody bez zmian): nieznana faza = `BLOCKED` `unknown_phase`, plan z fazą `[UI]` bez linii `Prototyp:` i bez obejścia = `BLOCKED` `ui_phase_without_prototype`, faza bez `[UI]` w planie z fazami `[UI]` = `PASS`; `--phase` bez `--plan` = `BLOCKED` (exit 2, błąd argumentów). `readiness --plan` z linią `Prototyp:` lub obejścia: FAIL bramki = `BLOCKED` z `Prototype gate FAIL: …` (wyjątek: plan z fazami `[UI]`: FAIL bramki nie dodaje pozycji, pola `uiPhasesWaiting`), BLOCKED bramki = `BLOCKED` z `Prototype gate BLOCKED: …`, PASS = bez pozycji.
`prototype login-link` (ten sam `emit`/`exit_code`, wynik zawsze `{schema: 1, status, …}`): `PASS` (0) z `url` i `expires`; `BLOCKED` (2) z `reason` i `code`: `server_not_running` (brak serwera projektu: brak pliku stanu, martwy PID, inny `instance` albo inny plik użytkowników), `ambiguous_server` (kilka serwerów projektu bez `--port`), `link_needs_loopback` (host serwera inny niż `127.0.0.1`/`localhost`/wildcard), `link_unavailable` (serwer z `--trust-proxy`: brak endpointu linku), `run_dir_unsafe` (katalog `run/` z prawami ≠ 0700, innego właściciela lub dowiązanie), `unknown_user` (konto nie istnieje; nigdy nie jest tworzone), `password_change_required` (konto z `mustChange`), `invalid_path` (`--path` poza dozwolonymi), `invalid_port` (`--port` poza 1-65535), `invalid_project` (błędny projekt lub manifest), `too_many_pending` (32 oczekujące tokeny), `users_unreadable` (nieczytelny plik użytkowników); nigdy `FAIL`, zawsze JSON z `schema` i `code` (także przy błędzie projektu lub portu). Brak `--user` i inne błędy argparse to exit 2 z usage bez JSON.
`prototype iterate|restore|comments|triage|decide|resolve|merge-comments` (ten sam `emit`/`exit_code`): `iterate` → `FAIL` (1), gdy `ids --check` bieżącego `index.html` nie przechodzi (nic nie zamrożone), `BLOCKED` (2) przy prototypie v1, istniejącym `iterations/N/`, `incomplete_restore` i stanie gita blokującym commit K40 (merge, rebase, cherry-pick, revert, konflikt, porażka `git add`/`git commit`; poza repo tylko ostrzeżenie). `restore` (także `--dry-run`, `--resume`) → `PASS` (także `result: unchanged` bez zapisu, gdy sekcja iteracji równa się bieżącej, D27) albo `BLOCKED` (2) bez zapisu z polem `error`: `iteration_not_found`, `screen_missing`, `ambiguous_section`, `ids_check_failed`, `incomplete_restore`, `--who` spoza pliku użytkowników albo bez roli acceptor/developer; nigdy `FAIL`. `triage`/`decide`/`resolve` → `BLOCKED` (2) dla wątku nieistniejącego, usuniętego albo ukrytego (`thread_not_found`), `triage` na wątku z decyzją (`thread_decided`), złego `--who`; `comments` → `PASS` albo `BLOCKED` przy złym `--status` i prototypie v1. `merge-comments` (obie formy) → `PASS` (także z `missingIterations`, to ostrzeżenie) albo `BLOCKED` (2) przy konflikcie (`merge_conflict`), innym `prototypeId` i złym formacie; exit ≠ 0 sterownika git traktuje jako konflikt i zostawia plik A bez zmian. Klucz manifestu `prototype.commit_before_iteration` innego typu niż bool → błąd sekcji (`BLOCKED` każdej akcji, `error` w `doctor`).
`prototype writing <slug> start|done|status` (ten sam `emit`/`exit_code`): `PASS` (0) z `writing` (`null` albo `{since, expiresAt, by}`); `BLOCKED` (2) z `error` i `reason` (`<kod>: <opis>`): `needs_migration` (prototyp v1), `lock_timeout` (zajęta blokada prototypu, ponowienie), `invalid_args` (zły `--ttl` albo `--by`; `--by` zaczyna się od litery lub cyfry); `FAIL` (1) nie występuje; nieznana akcja to błąd argparse (exit 2 z usage). Ważny marker zapisu zmienia wyniki innych komend: `prototype accept` → `BLOCKED` `writing_in_progress` (przed pytaniem o hasło i w `build`; przy `--project` z listą `writing`), `prototype gate` → `FAIL` z wpisem `missing` `reason: writing` i `screen: null` (per prototyp, także przy ważnych akceptacjach; linia obejścia nadal daje PASS), `prototype wait` nie zwraca `accepted`; serwer odpowiada 409 `writing_in_progress` (zob. `prototype-comments-server.md`).
`prototype question add|list|show|export|record|withdraw|url|wait|merge|migrate|purge` (ten sam `emit`/`exit_code`; szczegóły: `expert-questions.md`): `PASS` → 0, `FAIL` → 1, `BLOCKED` → 2, `TIMEOUT` (`wait`) → 3. `FAIL` (1) = magazyn odrzucił treść albo stan (400/404/409, np. zła ścieżka w `--origin`, `unknown_reference`, `already_answered`, `withdrawn`, `invalid_mode`, konflikt scalania, `record` ze złą linią speca (`record_line_mismatch`, `record_line_out_of_range`, `record_spec_unreadable`), zły `--after` `unknown_op`, `migrate` przy tym samym `id` z inną treścią); `BLOCKED` (2) = błędne wywołanie albo środowisko (zły format `--origin`, `secret_detected` bez `--force`, 507 `file_too_large`, 503, uszkodzony plik, `url`: `users_file_missing`/`users_file_invalid`/`no_expert_accounts`, `slug_required`/`slug_ambiguous` przy `add`, `migration_required` przy `record`/`withdraw`, `unassigned` i `verify_failed` przy `migrate`). `list`/`show`/`export` mają `status: PASS` obok `schema: expert-questions/1` (bez pola `status` `emit` daje 2). `prototype user roles` jak `passwd`: `BLOCKED` przy `user_not_found` i `invalid_role`.
`dashboard show|serve|metrics` i `approvals record`: `PASS` → 0, `BLOCKED` → 2 (zły argument, brak projektu albo przebiegu, dowiązanie na drodze `.skillsync`, odmowa zapisu, duplikat zgody, blokada pliku trzymana ponad 10 s; `serve` także port spoza 5100–5199 albo zajęty); nie zwracają `FAIL`. `serve` po Ctrl+C/SIGTERM kończy 0 z JSON `PASS`. `approvals wait` (odczyt zgód) → 0 przy zgodzie, 3 przy przekroczeniu czasu (zob. `dashboard-server.md`, `docs/dashboard-contract.md`).
`doctor`, sekcja `prototype:` (`prototype.py:validate_prototype`): błąd typu/pustej wartości/ścieżki poza repo/brakującego `theme.tokens_from` lub `theme.css` albo `commit_before_iteration` niebędące bool → `error`; nieznane klucze i brakujące `guidelines` → `warning`; brak sekcji nie daje findings.
`doctor`, sekcja `delivery:` (`delivery_mode.py:validate_delivery_mode`): zła wartość `mode`, `null`, nie-mapa lub zła nazwa `base` → `error`; brak `mode` (domyślnie `pr`), `direct` bez `base` i nieznane klucze → `warning` (exit 0).

`readiness` (także `--run-id`): `PASS` → 0, `BLOCKED` → 2 z listą `issues`; zapis `readiness.md` nie zmienia kodu. Niepoprawny `--run-id`
albo dowiązanie w `.skillsync`, `.skillsync/runs` lub katalogu przebiegu → `BLOCKED` z `reason`, exit 2, bez pliku.
`status` i ostrzeżenia `preImplement.warning` oraz `warnings` z `plan|spec approve` nie są statusami operacji i nie zmieniają kodu wyjścia.

`PASS` w `retro` znaczy tylko, że raport powstał; `NOT_RUN` znaczy brak danych (`no_data`, pusty magazyn), nie sukces.
Komendy synchronizacji kończą 0 także z `[warn]`/`[conflict]`/`[info]`; błędy jawne (`import`, `add`, `skills add`) dają 1.

`doctor`: `error` → `FAIL` (exit 1); same `warning` → `PASS` (exit 0). Przed pierwszym `link` zwraca `FAIL` (brak zainstalowanych skilli, `CLAUDE.md`, ról, `AGENTS.md`) — oczekiwane.
Ostrzeżenie „No checks selected; no validation was performed” pojawia się zawsze, gdy projekt nie ma żadnych kontroli (`plan_validation`).
`doctor` jest kontrolą statyczną — nie dowodzi, że aplikacja przechodzi testy.

`setup` (kreator maszyny): `PASS` → 0 tylko wtedy, gdy każdy krok przeszedł bez blokady i `layers check` zwrócił PASS;
`FAIL` → 1, gdy kroki przeszły, a `layers check` zgłasza problem (np. `symlink-in-layer`); `BLOCKED` → 2 przy złej fladze,
braku dostępu do `--org-source` (`git ls-remote` bez pytań, limit 30 s), nieznanej wersji core bez zdalnego tagu albo błędzie git.
`NOT_RUN` `setup` nie zwraca. `--dry-run` nie zapisuje, więc jego wynik nie jest dowodem skonfigurowania maszyny.

Dlaczego: PASS/FAIL ma znaczyć wykonaną i dowiedzioną operację; plan lub brak konfiguracji nie może wyglądać jak zielony wynik.

Wyjątki i przykłady: `validate --run` daje `PASS` tylko dla kontroli z policzonymi testami: zero testów, nieznana liczba (bez `success_pattern`) albo pominięte testy bez `allow_skips` → `BLOCKED`.
`smart-test` bez zmian lub bez komendy testowej → `BLOCKED`; niezmapowane ścieżki → fallback do wszystkich testów. `ci` z lokalnym PASS ma `ci_status: NOT_RUN`.
